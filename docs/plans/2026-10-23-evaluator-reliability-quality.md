## 4. Proposed contracts and scoring rules

### 4.1 Durable result versus failure

New scored success requires verified inputs, a permitted provider attempt, a completed non-blocked model response, strict validated content and a locally derived total/grade. Idea may return a valid score with an explicit `persistence: unavailable` warning if personal history could not be saved; it must not claim a saved ID. Team/Challenge scorecard success requires a confirmed completed record. A failed save is not a second provider request.

Proposed Idea input bounds: 64 KiB aggregate JSON body, 200-character title, 12k-character description, 2k tech stack, 12k architecture, 30k supplemental text and 6k custom rubric, with required strings checked before trim and unknown track values rejected. Other endpoints retain their supported form/link shapes with explicit type, MIME/magic-byte, URL, string and total-size validation. A file parser limit is not a promise that the hosting platform accepts uploads of that size.

Recommended failure envelope: `success:false`, `result:null`, an existing user-readable `error`, plus fixed `code`, `retryable`, `requestId` and optional known `retryAfterSeconds` / authorized record ID. No scores, grade, generic strengths or fabricated slide feedback. Status mapping: invalid input/track/rubric 400; invalid/expired token 401; forbidden 403; unknown target 404; duplicate/in-flight/uncertain prior attempt 409; unsupported/empty text or safety rejection 422; user/global admission limit 429; malformed provider output 502; unavailable key/provider/quota-store 503; deadline exhaustion 504. Distinguish user limits from provider quota with codes, not invented retry timing. Invalid supplied credentials never downgrade to anonymous access.

Do not run numeric deterministic evaluation on automatic failure or `forceFallback`. Proposed RC choice: retire `engine=heuristic`/`forceFallback` as new scored modes with an explicit unsupported-mode response and explanatory UI; retain historical heuristic records/functions only for legacy reading/tests. A future optional readiness checklist is separate work, not a disguised scored result. Founder approval of this product choice is requested below.

Existing result/history JSON gains a small versioned metadata object: schema/rubric version, selected track, actual analysis mode, requested/resolved model, total and per-attempt latency, and fixed failure/degradation codes. Use existing JSONB fields; never persist PDF bytes, API keys, raw provider errors or an entire provider response envelope. Do not overwrite old records to make them appear newly validated.

### 4.2 Rubrics and grounded feedback

| Evaluator/track | Category maxima | Authoritative grade boundaries |
| --- | --- | --- |
| Idea web_dev / ai_genai | 25 / 35 / 25 / 15, with distinct domain criteria | Top tier >=85; strong >=70; high risk <40; otherwise iteration |
| Idea generic / supported custom mapping | 25 / 25 / 25 / 25 | Same Idea boundaries; supported custom criteria must be explicitly mapped and normalized |
| Team PPT specialized | 25 / 35 / 25 / 15 | Strong >=88; promising >=72; major concerns <50; otherwise iteration |
| Team PPT generic / supported custom mapping | 25 / 25 / 25 / 25 | Same PPT boundaries |
| Practice Challenge | 25 problem / 25 solution / 30 architecture / 20 feasibility-impact-roadmap | Mastery >=85; strong >=72; developing >=55; otherwise needs revision |

Keep cross-product thresholds intentionally distinct and documented. Within each product, derive all totals and grades locally from the authoritative caps; ignore provider totals/grades. Reject missing, null, boolean, string, fractional, non-finite, negative or over-cap category values. Never clamp, guess a scale, award a default score or “repair” partial output with generic prose. Require strict object/array/string shapes and bounded lengths. JSON Schema support complements, not replaces, server validation.

Use the existing PPT rubric/mode patterns as the reference. Idea AI tracks must not penalize a valid classifier/vision/direct-model system merely for lacking RAG, agents or vectors. Do not impose universal databases/caching/team-size/gender requirements. Custom mode requires an actual supported rubric and explicit category mapping; return unsupported_rubric when it cannot be faithfully represented rather than inventing rules. Challenge's six topics are a supplied practice template, not six independent additive weights or proof that the submitted deck contains those physical pages. Challenge domain guidance remains tied to the actual challenge/problem/rules, not transplanted Idea categories.

Each category deduction must identify supplied evidence or explicitly say information was not provided/not assessable. Require evidence anchors: normalized text quotes must occur in the supplied text; PDF feedback must reference valid physical pages. Empty strengths are acceptable for unsupported submissions; do not force praise. Metrics and repository/demo links remain **claims in the submission**, never verified implementation/research facts. Exact quote/page checks cannot prove semantic truth of model observations: benchmark/human review remains necessary. Do not claim a schema validator eliminates hallucinations.

### 4.3 Presentation modes

- Idea is always text-only; the server sets that fact, independent of a client boolean. Do not describe visuals or measured runtime behavior not supplied.
- Team PPT retains native PDF analysis with actual physical pages, plus distinctly labeled extracted-text AI when valid text exists. A refusal/safety block is terminal, not a reason to route the same submission through another model or text path. Invalid/oversized PDFs must not bypass validation through another extraction strategy.
- Challenge remains **extracted-text analysis**, including uploaded PDFs; adding visual AI would expand scope. Reuse bounded extraction/downloads and preserve physical page identity where available. Reject image-only/empty Challenge text with actionable guidance, without synthesizing six empty slides. Do not present segmentation heuristics as verified physical slide positions. Proposed common PDF cap is 8 MB with 60-page/120k-character bounds, requiring aligned Challenge API/UI wording (currently the upload API accepts 15 MB).
- Legacy history without analysis metadata is “legacy / method not recorded,” not proof of visual inspection or modern strict validation. Explicitly flagged heuristic history is labeled heuristic and non-comparable. Avoid showing mode-less legacy results as verified AI exports. No historical leaderboard rewrite is proposed.

## 5. Provider policy and request-wide deadlines

Official documentation checked October 23, 2026:

- [3.6 Flash](https://ai.google.dev/gemini-api/docs/models/gemini-3.6-flash) and [3.5 Flash-Lite](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite) document stable text/PDF inputs and structured output. Use pinned model names, not hot-swapped latest aliases; record returned modelVersion as well.
- [GenerateContent error reference](https://ai.google.dev/gemini-api/docs/generate-content/api-errors) distinguishes request/auth/billing errors, quota limits and service failures. [Retry guidance](https://ai.google.dev/gemini-api/docs/troubleshooting) recommends bounded retries for transient failures. [Structured output documentation](https://ai.google.dev/gemini-api/docs/structured-output) supports required schema fields. Stay on the existing GenerateContent REST integration; do not migrate to another SDK/API during this RC.

Proposed evaluator policy: text primary `gemini-3.6-flash`, at most one eligible secondary attempt using `gemini-3.5-flash-lite`. Native PDF starts with pinned `gemini-3.5-flash-lite`, preserving the current lightweight document strategy without asserting today's dynamic alias resolution. A permitted PDF-to-text degradation consumes the second and final request attempt; do not then start another independent text cascade. No attempt is made solely to replace invalid scores, improve a grade or evade refusal. Preserve image moderation's model/cascade behavior; regression-test the shared key-helper boundary without refactoring moderation.

Stop on 400/401/402/403, configuration/model-not-found 404, safety refusal and invalid/incomplete output. Treat unknown/daily/spend-exhausted 429 conservatively as unavailable, without model hopping. Retry only an identified short-lived rate condition with a usable bounded Retry-After, or a transient network/5xx/timeout failure, and only if cancellation/deadline/budget permits. At most two provider attempts, with one 250–500ms jittered wait when applicable. Parse every non-thought text part; require a completed STOP response. Forward `responseJsonSchema` on text as well as PDF requests. Use header authentication, not API keys in URLs. Require server-only `GEMINI_API_KEY`; do not create, rotate or edit environment variables here.

Start one deadline at each handler entry, not at each model call: retain 60s maxDuration and reserve the last 5s for persistence/reconciliation. Proposed usable work deadline is 55s: up to 5s admission/auth/input work, up to 15s bounded ingestion/parsing, at most 30s combined provider work, and remaining persistence reserve. Every stage uses min(its cap, remaining request time); waits, streamed bodies, callbacks and response decoding count toward the same deadline. Pass cancellation/deadline through provider and extractor calls; no attempt starts with insufficient remaining time. Validate negative/non-finite timeout/attempt settings. Fake-clock tests establish bounded control flow; actual provider/network latency remains unmeasured.

Observability uses a fixed allowlist: random request ID, pipeline, rubric version, attempted model/resolved version, mode, stage, sanitized code, HTTP status, attempt count and elapsed milliseconds. Do not log titles, deck/source URLs, text/PDFs, person/team names, raw provider messages, tokens, service keys or full request bodies. Catch blocks handling Supabase errors must log the failure through a sanitizer that retains safe error code/operation; do not silently interpret them as empty rows. Error responses use the same sanitized taxonomy. Existing shared vision logging behavior is outside this evaluator change; do not claim all historical application logs are sanitized.

## 6. Admission, concurrency and idempotency without new schema

### Reuse subject to deployment verification

Before deploying RPC-based controls, independently read and review the deployed `check_rate_limit` definition, ownership, fixed search path, unique key on `rate_limits.ip` and execution grants. Its deployed implementation must use the reviewed atomic INSERT ... ON CONFLICT pattern and be callable through the existing service role only. No permission broadening, function replacement or migration is included. If missing, malformed or inconsistent, stop/fail closed and request separate database approval; do not fall back to the racy app_settings counter or process memory.

Namespace new keys separately from contact/email limits and from other evaluators. Bound key lengths and use pseudonymous actor keys derived server-side, not raw IPs or client IDs. Do not log keys. Use stable global keys and existing server-held secret material for keyed actor digests, with rotation/erasure implications documented; no new credential. Reset anonymous/Idea daily admission at UTC midnight, preserving the advertised day semantics; other current 24-hour controls must document whether the existing RPC's fixed window is conservatively suitable rather than claiming it implements an exact sliding window. Never silently relax a limit by approximating it.

For each admitted request: validate target/identity first; reserve a namespaced idempotency token, actor/target allowance and an active-execution slot, then call the provider. Retry attempts within the same logical request do not reserve a second actor allowance. For Idea, reserve the global provider-attempt allowance immediately before **each** network attempt; uncertain/failed provider execution is not refunded. This removes lost increments and prevents retries from evading the nominal cap. The 100-attempt Idea budget is not silently extended to every Gemini consumer.

Retain the existing team/Challenge rolling 24-hour history checks **after** shared actor/target active-slot admission, and fail closed on count/version query errors. Serialize all relevant actors/targets before those reads, so replacing them with a fixed-window counter cannot introduce a boundary burst or concurrent version race. The existing RPC is an additional conservative attempt limiter, not evidence of exact sliding-window semantics. Any limit/window change requires an explicit founder decision rather than a silent approximation.

Use an explicit client-generated Idempotency-Key, stable across uncertain network retries and namespaced to the verified actor (or safe anonymous identity). Duplicate tokens return 409 with history/recheck guidance; do not re-run the model or claim the old operation completed. A confirmed terminal response can clear the client token for a later explicit submission. After an unknown response, do not silently rotate the token and resubmit. Bound duplicate-token retention/window, proposed 24 hours; no perpetual content-hash archive. A short active slot, proposed 75 seconds for a <=60s handler, serializes team/challenge versions across members. Its post-completion remainder is a disclosed cooldown, not a false claim that evaluation is still running. No new scheduler is needed.

The existing counter RPC cannot atomically reserve several keys as one transaction, store an outcome for replay, or release a lease. Partial reservations may conservatively consume an allowance when a later check fails. Do not promise exactly-once execution or automatic replay of the original response. Cross-instance replay after the idempotency window is a new explicit attempt subject to current limits. If precise refundable quotas, exact sliding windows, transactional multi-key admission or durable result replay are required, they need a separately approved reservation/RPC migration. No such migration is written/applied in the minimum candidate. The implementation must fail closed if safe admission cannot be established with the verified deployed contract.

Small fixed counters/short idempotency keys reuse existing storage, but pseudonymous keys remain privacy-relevant. Review erasure and existing rate_limits cleanup behavior before enabling new production namespaces. Prefer explicit expiry-aware reads and the existing approved erasure/cleanup path; do not add an unapproved scheduler or claim expiry automatically deletes rows. If existing cleanup cannot enforce the agreed key retention, hold that production capability for a separately approved remedy. No submission text or raw fingerprint is stored in limiter keys.

## 7. Persistence, stale processing and track compatibility

Team PPT should retain a validated record ID outside the engine try block. Both initial creation and completion require exactly one intended record, valid ID and appropriate status. Write initial `ai_feedback` track/version metadata even when the column is absent. Complete with a conditional update matching ID, team and `status=evaluating`; confirm the returned row. A catch after initialization attempts a bounded conditional transition to `failed`, with fixed `error_message`, mode/failure metadata and updated_at. Never overwrite a concurrently committed `completed` record.

When a completion response is uncertain, re-read the authorized record within the remaining budget before claiming success/failure; do not run the model again. If DB reconciliation also fails, return a distinct persistence_uncertain error and keep the ID available to the authorized client for history recovery. Logging a failed cleanup is mandatory. Catch/finally cannot run after hard termination, so the UI recognizes aged processing state as interrupted instead of spinning indefinitely. On an explicit authorized POST/retry, conditionally mark rows older than a conservative stale cutoff (proposed 120s, beyond the handler/slot lifetime) failed, then re-read active status before initializing. No repair writes from GET/report handlers, no scheduled cleanup and no mass historical repair.

Challenge failures before insertion create no completed scorecard. Replace its ineffective pre-AI status check with verified admission/idempotency/active-slot controls. Confirm a successful insert before celebration/navigation; retain draft input after failures. Correct exact target and team mode validation before extraction/provider work. Do not choose the latest challenge or infer a missing team ID. Version races need per-team/per-challenge serialization plus verified reads; existing non-unique version indexes alone do not provide that guarantee.

For `track_id`, preserve the specific 42703/PGRST204 + track-column compatibility branch and retry at most once without that optional column. Do not retry unknown insert failures that may already have committed. New complete JSON metadata records the actual resolved track, rubric version, category labels/caps and custom mapping regardless of column availability. Validate saved track names; conflicting metadata is an explicit compatibility warning, and missing historical metadata is “unknown rubric,” never guessed web_dev. Keep the current list-route fallback; no need to replace its API or permissions.

Do not apply migration `20260905210000` to solve the deadline. Its historical default and CASCADE view recreation require a separate deployed/repository drift audit, dependency/privilege inventory and safe forward-only migration review. No historical default/backfill is justified by missing evidence.
