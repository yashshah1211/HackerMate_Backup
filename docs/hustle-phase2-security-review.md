## Spec

The review found one functional defect: cookie-session refresh updates were discarded on the new standalone organizer routes, which are outside the existing middleware's generic organizer matcher. Fixed by adding an optional cookie-update callback to the shared verified-profile/partner helpers and wrapping private Round 2 responses to persist updates on both successful and denied requests. Existing callers retain their default behavior. Tests cover an actual expired cookie, refresh-token rotation through the installed Supabase SSR client, and a follow-up authenticated request without a bearer header.

Additional privacy hardening changes generated links to `/partners/hustle-carnival/phase-2/invite#<secret>`. Fragments are not sent in HTTP request targets. The standalone landing page immediately removes the fragment with `history.replaceState`; it contains no token in server-rendered HTML and performs no database lookup on GET. An explicit same-origin POST exchanges the in-memory secret into an HttpOnly/SameSite cookie. Only hashes reach the database. Old token-path URLs are not issued and return a generic 404; no real invitations were issued during development. Regression checks compare raw tokens against HTTP URLs and Next access logs.

Follow-up independent review found no actionable defects in either fix. Standards findings: 0. Spec findings: 1, fixed; worst initial finding was cookie-refresh loss (P2).

## Targeted production-permission compatibility fix

The reported release blocker was independently reproduced in disposable PostgreSQL: with service_role configured as a non-superuser BYPASSRLS role, SELECT only on profiles(id, role, is_banned), no SELECT on auth.users.id/email, and no EXECUTE on has_partner_admin_access(), the original invoker helper makes the admin import RPC fail with SQLSTATE 42501, `permission denied for table users`. The previous fixture incorrectly granted broad auth.users SELECT and concealed this incompatibility. This is a local reproduction of the supplied production ACL configuration, not a new audit or modification of connected Supabase.

The minimal fix changes only `hustle_phase2_authorized(uuid, boolean)` to SECURITY DEFINER in the still-unapplied migration. It returns one boolean, reads explicitly qualified profiles(id, role, is_banned) and auth.users(id, email), uses `SET search_path = ''`, and retains EXECUTE only for the trusted owner and service_role. PUBLIC, anon and authenticated remain denied. No dynamic SQL, new table grant, auth.users SELECT grant, existing predicate change or widened mutation privilege is introduced. This follows the [Supabase function security and privilege guidance](https://supabase.com/docs/guides/database/functions#security-definer-vs-invoker). The server still obtains p_actor from verified getUser identity and protected profile data; a browser-supplied actor cannot reach privileged RPC execution.

Founder/admin semantics are unchanged: a matching protected profile, explicitly false ban flag and nonempty authoritative auth email are required; authorization is role=admin or the exact lowercased/trimmed founder email. Unknown/null actors, missing profiles, empty/null email, banned or unknown ban state, founder near-matches, and false/null write flags deny. Only the existing exact founder policy constant is used on a synthetic fixture UUID; no real account or contact is queried or messaged.

All four administrator mutation RPCs remain SECURITY INVOKER: import, activate, invite and revoke. Real PostgreSQL tests execute all four successfully as service_role for both an admin-role identity and the founder exception, including foreign-key and audit writes, without raw auth.users, hackathons or event_organizers SELECT. Each RPC also denies browser-role forged-admin calls, unrelated/organizer actors, banned admins and banned founders. The causal regression temporarily restores invoker mode inside a failed transaction, asserts the original 42501 and rolls it back. Tests inspect the helper owner, return type, empty search path and ACL; existing caller-only predicates remain non-executable by service_role. Anonymous/authenticated raw-table ACL/RLS denial, organizer event isolation, expiry, replay and concurrent responses remain covered.

Review of other permission assumptions found no additional grant change needed: UUID defaults use built-in gen_random_uuid (no sequence grant); FK checks do not require caller SELECT on referenced identity/event tables; the migration supplies the necessary privileges on its five new tables; audit access remains append-only for service_role. Roster authorization continues through authenticated caller JWT and its narrow definer projection, never the service-role client. Deployment must preserve a trusted migration owner with protected identity read/RLS access; function ownership and the existing partner predicates still need verification in a separately approved schema-compatible integration environment. A disposable PostgreSQL/Auth adapter is not a complete hosted Supabase/PostgREST deployment.

Final compatibility-fix rerun: TypeScript and scoped ESLint passed; 492 unit/regression tests (20 Round 2 + 472 existing), 167 real SQL checks, and 47 browser/API/SQL checks passed, including synthetic core-page smoke checks and PR #26 portal/workshop compatibility. The expected old-code reproduction failed as designed; the only intermediate new test defect was CRLF parsing in its assertion, corrected before the final run. Production and Preview remain source-hard-disabled; the public participation guard still returns false. No dependency or application runtime code changed in this targeted fix.
