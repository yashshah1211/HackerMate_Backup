## Architecture and authoritative semantics

`audit` is a new private schema. Three tables hold detailed facts, compact account landmarks, and coverage/cleanup state. They have enabled and forced RLS, no ordinary-role schema/table access, and no ordinary-role policies. Service role has private SELECT for the SECURITY INVOKER aggregate and no direct table write privileges. Internal definer writers/triggers are postgres-owned, have pinned `pg_catalog, audit` search paths, and cannot be executed by anon, authenticated or service roles. New public rejection is authenticated-only; cleanup and aggregate RPCs are service-only. Existing table grants, policies, authentication, token validation and notification delivery are unchanged. Never add `audit` to exposed PostgREST schemas.

The CLI generated `supabase/migrations/20261023130455_team_formation_outcomes.sql`. Migration preconditions compare normalized deployed function bodies, owners and exact execution ACLs, and fail on drift. `deployed-functions.json` contains the read-only capture of all six relevant functions. The token implementation deliberately retains its deployed notification and retains invitations; it does not copy the drifting repository token body. A bounded cutover lock excludes concurrent profile/team/request/membership/invitation writes while baselines and triggers are installed. All changes commit or roll back together.

| Fact or metric | Definition |
| --- | --- |
| Request submitted | A durable INSERT of a pending request after cutover, keyed by its database UUID. Baseline or non-pending imported rows are not new submissions. |
| Accepted/rejected | Explicit authorized owner decision inside its successful database transaction. Acceptance also requires the actual resulting membership UUID; rejection locks the request and current owner team, deletes one pending row, and returns its UUID. |
| Superseded | An existing pending request removed by successful invitation or signed-link membership. It never counts as owner acceptance/response. Non-pending legacy cleanup retains its existing unclassified fact and cannot prevent valid joining. |
| Unclassified | Direct/legacy removal or unsupported status change without an explicit decision. Missing or identity-mismatched facts remain measurement gaps; disappearance never establishes rejection/acceptance. |
| Still pending | A matching current pending row, including the original team and applicant identity. Absence of a terminal fact alone is insufficient. |
| Confirmed membership | The actual committed membership episode UUID. Authorized wrappers classify owner creation, request acceptance, invitation or signed link. Deferred insert fallback records unattributed acquisitions; same-transaction enrichment cannot rewrite older history. Removal has its own fact. Role/project-role changes are not acquisitions. Identity reassignment is flagged separately, never invented as another acquisition. |
| First-team activation | Exactly one compact activation landmark per eligible new account. Registration uses `auth.users.created_at`, not a profile/client timestamp. Existing accounts, delayed old profiles and unknown/future registration times are excluded and counted. Concurrent acquisitions serialize per account. Reassigned first memberships remain unattributed, rather than falsely claiming a later first activation. |
| Cohort | Half-open UTC `[start,end)` submission/registration window. Default is UTC midnight 35 days ago through midnight seven days ago. Requests younger than seven days are immature and excluded from mature rates. |
| Seven-day owner response | Explicit accepted/rejected decisions at or before creation + seven days, divided by **all** mature submitted attempts, including pending, late, superseded and unclassified attempts. An exact seven-day response qualifies; one second later does not. |
| Request conversion | Mature attempts with an actual matching membership acquisition linked by their canonical accepted/superseded fact, divided by all mature attempts. Request and membership counts are different units; multiple applications by a person remain separate attempts. |
| Decision time | P50/P90 hours from creation to explicit owner decision for mature submission-cohort requests. Unknown/negative intervals are not assumed durations. |
| First activation rate | Activations at or before registration + seven days / all mature eligible registrations, including non-joiners. Creator, joiner and unattributed sources remain separate. |
| Pending age | Current pending count; P50/P90 age; strictly older than seven/fourteen days; missing/future timestamps separately unknown. These are descriptive age buckets, not values inferred from the historical October audit. |
| Collaboration | Current teams with at least two distinct members; a solo creator is not collaboration. |

The existing admin boundary verifies caller identity, protected role/ban state and founder semantics before creating a privileged client. The new endpoint refuses the existing RLS-limited fallback, validates bounded UTC windows, returns a fixed aggregate DTO without identifiers, and sets `private, no-store`. Its SQL report uses one statement snapshot. The existing attention page adds an on-demand table; account changes abort and clear the new report. Partial coverage hides rates instead of presenting missing history as zero. Erasure revises surviving denominators and is explicitly disclosed; no anonymous historical aggregates are retained.

## Retention and erasure enforcement

Detailed rows are physically deleted at **88 days from recording**, leaving a two-day margin before the approved 90-day maximum. Only a non-PDF GET with the validated existing cron credential calls the service-only `prune_team_formation_history` before its existing reporting work. It validates the result, logs actual failures, and continues the existing report/email flow. There is no new schedule, vendor, notification or automatic outreach.

The report shows the last successful cleanup, becomes partial after 36 hours without cleanup, refuses a report if any detailed row reaches 90 days, and refuses windows older than 87 days. This prevents expired/partial history being labelled complete; refusing a read is **not** a substitute for physical deletion.

Before release, an operator must verify the existing daily job is active with the correct service credential and verify its first cleanup/next scheduled cleanup. Check its existing logs and cleanup timestamp daily. If cleanup fails or reaches 36 hours stale, an authorized operator must restore the existing job or execute the approved service-only cleanup before any detail reaches 90 days, then verify no expired rows remain. A scheduler outage beyond the two-day margin would breach retention unless the operator intervenes: this is an explicit operational release prerequisite, not a claimed hard timer guarantee. No additional alert or scheduler is installed automatically.

Compact registration/first-activation markers are account-linked, not anonymous. Both marker and detail subject links have profile FKs with `ON DELETE CASCADE`. The existing hard account-erasure path deletes profiles; local tests delete the synthetic Auth account and verify that profile, marker and all journal subject links disappear. Team/request/membership references have no source-row FK cascade, so ordinary leave/disband does not erase historical outcomes. They carry no owner/actor identities, names, emails, content, tokens or IPs. A suspension/soft deletion is not erasure: applicable erasure must use the existing verified hard-erasure path and verify the private relations too. Backup/PITR retention and erasure replay after restoration require operational privacy sign-off before release; these provider settings were not changed or verified. Do not retain anonymous longer-term aggregates without separate review.
