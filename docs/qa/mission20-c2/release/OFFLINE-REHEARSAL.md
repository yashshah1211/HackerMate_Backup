## Intended loader and transaction ownership

Proposed future mechanism: **pinned Supabase CLI 2.75.0 `migration up --db-url …`**, direct PostgreSQL session, reviewed complete migration inventory, one newly authorized stage per invocation. Do not substitute `db push`, Dashboard SQL, MCP apply, a pooler transaction endpoint, or another CLI version without requalification. 2.75.0 is an explicit tested pin, not a claim that it is current. The founder must approve the pin and actual privileged operator/session model. No existing production loader had previously been specified or verified.

Official pinned sources: [file.go](https://github.com/supabase/cli/blob/v2.75.0/pkg/migration/file.go), [apply.go](https://github.com/supabase/cli/blob/v2.75.0/pkg/migration/apply.go), [history.go](https://github.com/supabase/cli/blob/v2.75.0/pkg/migration/history.go), [connection selection](https://github.com/supabase/cli/blob/v2.75.0/internal/utils/connect.go). The loader splits SQL, sends statements plus its ledger INSERT in one extended-protocol batch, and processes migration files separately. Its ledger stores version, name and statements; it does not verify our SHA manifest itself. A duplicate version or changed already-applied file must never be treated as proof of source equivalence.

**Important packaging correction:** the existing standalone candidate's explicit COMMIT can commit DDL before the CLI appends its ledger INSERT. A failed ledger insert can then leave installed objects without a receipt. That file remains an immutable psql transaction artifact; it is **not** an atomic CLI migration. The new `loader/*.review.sql` artifacts remove only each source's single outer BEGIN/COMMIT. The CLI owns the transaction including the receipt. Every other parsed SQL statement is preserved exactly. Source and packaged hashes are in [LOADER-MANIFEST.json](loader/LOADER-MANIFEST.json), regenerated by `node scripts/mission20-loader-package.cjs --write-review-only`. Original source files, hashes, guards and existing candidate are unchanged.

Tentative versions remain `20261102090000` freeze, `20261102090100` expansion, `20261102090200` contract, `20261102090300` unfreeze. These are not reserved/active migrations. Recheck the full live ledger and allocate proper filenames only with separate authorization. The expansion guard expects 147 baseline receipts plus the separately committed freeze. Any new migration requires version/guard/package review, not ledger repair.

For a future release, stage only the approved next file alongside the **complete, reconciled historical inventory**. Stop and save its object/ACL/ledger receipt before staging another. Never put unfreeze and expansion into one pending batch: the CLI applies every pending file and would bypass human gates. The local harness creates 147 poison-pill historical files matching its synthetic ledger; none executes. They are not historical production migrations and are never copied to the repository.

## Disposable execution and recovery

Run `node scripts/qualify-mission20-offline-release.cjs`. It accepts no connection/SQL/file/credential arguments, inherits no Supabase credentials, reads no `.env`, does not link a project, and uses only fresh loopback PG17.6 allocations. The checksum-pinned CLI must exist at ignored `scratch/supabase-cli/supabase[.exe]`; archive hashes are in the loader manifest. External HTTP(S) proxy routing is denied in the child process, CLI home/profile paths are temporary, and local CLI port selection is explicit. It does not start Supabase services or Docker. All clusters/dumps/temporary migration packages are removed by the existing guarded `finally` cleanup.

The rehearsal requires these real database outcomes:

1. pg_dump custom backup of synthetic pre-freeze schema, ACLs and data, including team-linked confirmed and waitlisted registrations.
2. Actual CLI commits freeze + ledger receipt, independently visible before expansion.
3. Raw explicit-COMMIT candidate reproduces committed expansion with absent receipt on injected ledger failure. This is an asserted unsafe diagnostic, never hidden as success of that packaging.
4. Restore pre-freeze backup into a new disposable database. Compare complete registration JSON, ledger and prior ACL/object state.
5. Loader-packaged expansion rolls back ALL final DDL and receipt on ledger-only failure and on a final SQL error; earlier freeze and every registration remain intact.
6. Terminate the actual loader backend at a controlled precommit sleep after DDL. Confirm no expansion namespace/RPC/receipt survives and freeze/data survive. Reconcile before retrying.
7. Success commits final protocol and ledger together. A subsequent CLI invocation sees no pending stage; this models read-only reconciliation after an unknown/lost success response, not automatic replay of destructive actions.
8. Separate contract and unfreeze calls record separate receipts and restore only the reviewed community column ACLs. The synthetic exercise does not approve the real community outage.
9. Emergency refreeze, then backup/restore final state into another new database: final protocol, admission restrictions, ledger and existing registration data retained.

This is a **logical synthetic fixture restore**, with same-cluster roles already present. The inherited fast fixture starts PostgreSQL with fsync off; interruption is a backend/transaction termination, **not** a power-loss/WAL durability proof. It does not qualify production backup access, cross-cluster globals/role ownership restoration, encrypted storage, extensions/binaries, WAL/PITR, managed Auth/Storage services, realistic data volume, backup retention or operator RTO/RPO. Actual production-backup/PITR readiness and a separately approved secure restore procedure remain blockers. A pre-freeze backup contains vulnerable old direct-write ACLs: never publish it as a recovery target until it is isolated and freshly frozen/secured. Do not overwrite newer production writes or assume a dump can reconstruct intentional account/team CASCADE deletions.
