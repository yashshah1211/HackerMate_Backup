## Deterministic two-session concurrency protocol

Implement this in the existing disposable local runner using two independent psql processes/connections, explicit BEGIN/COMMIT, readiness/output barriers and process timeouts. Do not replace concurrency with serial calls or a JavaScript mutex simulation. Use fresh fake IDs per case and destroy the cluster in finally. Parent process must record SQLSTATEs, output, committed row counts/statuses and zero unexpected rows. A third connection can inspect wait state/pg_locks; no access to a real project.

1. **Last slot:** fixture approved native E, cap=1, two valid users A/B. A begins, calls RPC and gets confirmed but holds its transaction open. Signal an explicit barrier only after the function returns. B begins and calls the RPC; assert it blocks on E. A commits; B must return waitlisted. Commit B; verify exactly one confirmed and one waitlisted, no duplicate identities. Repeat with 20/100 distinct contenders and community writes to the same non-native event, including forged status values.
2. **Rollback releases slot:** same schedule, but A rolls back. B must confirm. No phantom consumed slot or leaked lock.
3. **Same actor retry:** A holds a successful RPC transaction; B calls the same event/user/team. After A commit B returns alreadyRegistered=true with the existing status, and every original timestamp/preference/metadata/team remains unchanged. After A rollback B creates exactly one row. Also test RPC retry racing self-cancellation; interpret results in commit/linearization order, not as a promise that later cancellation cannot remove the row.
4. **Deadline while waiting:** administrative A locks E before the next caller. Set a cutoff within a bounded wait (<3s), start B before it, release A after the cutoff. B must reject and insert nothing. Starting the transaction before the deadline must not substitute transaction-start now() for a fresh clock. Repeat date-only India midnight with the fixture's boundary helper and controllable scheduling; real-time qualification may require a short synthetic timestamp cutoff rather than changing the server clock.
5. **Approval/archive/deadline edit:** A holds E, changes approval/archive/deadline, then commits. B must observe the committed restriction after waiting. Reverse order: admitted A commits before administrative change; its row remains and later callers are denied. No retrospective deletion is permitted.
6. **Capacity edit:** A admits under E's lock while B tries to reduce cap below resulting confirmed count: reduction must fail. Reverse order, setting cap=0 first: new callers waitlist. Unlimited→limited, concurrent DELETE and rejoin, duplicate INSERT and ON CONFLICT attempts must not exceed cap.
7. **Roster:** native A holds selected-team eligibility and reaches an event-lock barrier while B attempts INSERT/DELETE/UPDATE of that roster. Roster mutation waits until admission commit/rollback; counted owner + distinct members are correct. Another unrelated roster writer also waits, documenting the global SHARE cost. Multiple native readers can coexist. A later roster change after admission remains permitted; no claim of lifelong eligibility.
8. **Locks/deadlocks:** cancellation/admin event or user cascade/team deletion in opposite event order, roster mutation triggers and representative batches. Test 55P03, 40P01, timeout, client disconnect and aborted transaction. No partial registration/approval update; retries reauthorize/recheck dates. Record actual whole-request timeout behavior. Other isolation levels must fail with 25000 before admission or a capacity reduction, rather than counting from a stale REPEATABLE READ snapshot. Include bulk direct community INSERT/UPSERT and bursts to the RPC itself: HTTP-only throttling cannot be the sole abuse control for a callable database API. Verify existing platform body/runtime limits and measure starvation without adding a billed dependency.

Capacity invariant applies to **new accepted operations on a clean fixture**, not to a grandfathered event already over capacity. The reviewed admission linearization point is the final restriction check before insertion under the event lock; committing after a deadline is allowed if the decision preceded it. If the founder requires commit-time cutoff instead, redesign and test that requirement before implementation.
