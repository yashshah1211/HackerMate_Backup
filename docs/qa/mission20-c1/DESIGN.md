## Intent, assumptions and decisions

- Bind native registration to a verified active account, an approved/unarchived native event, fresh registration/event restrictions, owned-team eligibility and an atomic capacity decision.
- Keep the founder's **Review registration** flow: unknown availability needs explicit acknowledgement; known restrictions always reject. Acknowledgement is not proof of openness or guaranteed admission.
- Preserve external/legacy `official` HackerMate community participation. A community row, `confirmed` status or team association never certifies external organizer admission.
- Preserve private registration readers, existing preferences, safe track metadata, self-cancellation, partner/certificate/team records and administrative workflows.
- Use existing PostgreSQL/Supabase and test infrastructure. No payment/provider/API dependency or environment change is proposed.
- Assume PostgreSQL 15+ and **READ COMMITTED** for admission and capacity reductions; those checks reject other isolation levels. A later release must confirm actual server version, types, ACL inheritance, policies, triggers and owners. The repository is a migration history, not a complete live-schema dump.
- Capacity recommendation: retain current values as a legacy **confirmed registration-row slot limit**, without calling that a human or team quota. The field/UI label max_participants is ambiguous; C2 must clarify terminology and the founder must approve the compatibility interpretation. One owner registration with four roster members still consumes one row slot. No value/status/data rewrite is proposed. Throughput, whole-request timeouts and production-scale behavior remain acceptance gates.

| Decision | Recommendation and reason | Alternatives / review gate |
|---|---|---|
| Native writes | Restricted RPC + private worker; direct native INSERT denied by restrictive RLS | Trigger-only native writes preserve the bypass surface and cannot carry explicit unknown-review acknowledgement reliably. All-RPC community writes would require a wider client cutover. |
| Community writes | Retain the exact legacy INSERT column payload, restricted to approved/unarchived external/official rows; trigger derives status | The retained column grant alone is not the authorization boundary. RLS and the trigger jointly make it safe. |
| Atomicity | Lock the event row, then read authoritative confirmed count and insert in the same transaction | App pre-checks and RLS count subqueries alone are race-prone. A counter table adds reconciliation/schema complexity. |
| Team roster | Writer entry points pre-lock complete parent sets before child DML; row trigger uses NOWAIT for legacy child-first conflicts | A blocking BEFORE row trigger alone is insufficient with the confirmed CASCADE graph. Global and old per-team 40P01 diagnostics remain. Current 07/08 prototypes bound the tested inversion without adding base-table authority. |
| Privileged worker | Existing postgres owner, empty search_path, fixed SQL, minimal public inputs/outputs; no new table grants or role memberships | This is a deliberately privileged trust boundary, consistent with existing projection functions. A dedicated function-owner role needs additional auth/profile/team ACL and RLS design, including row-lock privileges; it is not silently introduced. Independent approval of this boundary is required. |
| Approval | Server/admin service-role transitions; owner creates native pending, external approved, and cannot mutate type/status/review identity | Blanket pending for all events would break external cross-listing. Owner archive/deadline/content edits remain available; type/status and review metadata stay protected. |
| Rollback | Freeze admission and fix forward, preserving tightened access | Restoring unsafe direct native grants/policies is not an acceptable automatic rollback. |

## Proposed database boundary

Read the release sequence together: [admission freeze](sql/00-freeze-admission.proposed.sql), [01 expansion](sql/01-expand.proposed.sql), [per-team admission](sql/05-per-team-roster.alternative.sql), [writer protocol](sql/07-writer-protocol.proposed.sql) and [existing writer corrections](sql/08-existing-writers.proposed.sql) while frozen, adapter release, [02 contract](sql/02-contract.proposed.sql), then independently gated [unfreeze](sql/06-unfreeze-admission.proposed.sql). | Role / path | End-state access |
|---|---|
| anon / PUBLIC | No registration INSERT or native RPC EXECUTE. Existing public safe projections remain. |
| authenticated direct INSERT | Only own approved/unarchived external/official community row, owned optional team, existing allowed metadata. A restrictive policy prevents permissive-policy OR bypass for native writes. |
| authenticated RPC | `register_native_hackathon(uuid,uuid,boolean)` only; identity/status are not arguments. Internal worker also authenticates/authorizes independently. No client EXECUTE on helpers or trigger functions. |
| authenticated UPDATE / DELETE | Existing own preference columns and metadata guard; identity/status/team immutable; cancellation remains. Confirmed team FK CASCADE deletes linked registration rows; there is no SET NULL preservation exception. |
| trusted service/admin | Existing read/delete/approval workflows retained. No new service grants. All new registration INSERTs must have a valid matching actor and derive status; status changes require a future promotion mechanism. |
| postgres owner | Privileged maintenance authority outside client threat model. New definer bodies use fixed qualified SQL and empty search_path; no caller-provided SQL. |

The private schema must not be Data API exposed. Authenticated USAGE/EXECUTE on only the private worker is needed by the SECURITY INVOKER wrapper; private schema location is not relied on as authorization. Even a direct SQL call to that worker must pass the same checks. Future catalog review must verify every overload/owner/ACL and schema CREATE privilege. No configuration is changed here.

### Atomic admission and clocks

Recommended per-team mutating admission takes account row locks, the parent team FOR UPDATE, then the event row FOR UPDATE; count and insertion follow as separate commands within the transaction. Membership writers take affected parent locks before mutation, and the existing matchmaking AFTER hook takes compatible reentrant NO KEY UPDATE locks. Existing-registration retries use an event-locked read path without subsequently acquiring a parent; if a concurrent cancellation removes the row, return a retry error. The trigger derives confirmed/waitlisted from authoritative row capacity. The global comparator has different ordering and is not eligible for unfreeze.

Event approval/archive/deadline UPDATEs take that event row lock too. `clock_timestamp()` is sampled after blocking checks and again after capacity counting, rather than using transaction-start `now()`. The admission decision immediately before insertion is the linearization point: a registration checked just before the cutoff may commit afterward. Approval/archive changes afterward do not retroactively erase accepted registrations. Existing over-capacity rows are not repaired; catalog/data preflight and an explicit reconciliation decision are release blockers.

Date-only values use the next Asia/Kolkata midnight as exclusive end, and the same day's midnight as start. Explicit-offset timestamps retain their instant and PostgreSQL precision; no extra day is added to stored timestamp cutoffs. JSON conversion handles date/text/timestamptz input shapes without assuming a registration_status column exists in an older schema. Invalid or naive values become unknown; explicit closed status and any confirmed future start/past deadline/event end still reject. Unknown is permitted only through acknowledged native RPC. Already-corrupted historical timestamp dates cannot be reconstructed automatically.

The internal clock-injected assertion helper enables exact future SQL tests at cutoff equality and one microsecond either side; clients cannot execute it. Admission always calls the database-clock wrapper, and the public/private registration entry points accept no time override. Actor checks reject current profile bans, Auth bans, soft-deleted/anonymous accounts and missing email. They do not claim immediate JWT/session revocation beyond the existing platform contract.

Both global and old per-team 40P01 schedules are reproduced with the confirmed production member/conversation CASCADE graph. BEFORE row triggers cannot acquire parent locks before the executor's target-tuple lock. Current writer prototypes pre-lock complete sorted teams, then affected events before child DML; legacy membership writes, registration DELETE and late successor-profile locking use NOWAIT. Revised tests either commit in order or roll back with explicit 55P03, including participant DML and user deletion. Source authorization checks are retained exactly and invoker wrappers retain real RLS. This bounds the tested risk; PG17.6, full deployed graph, outer timeout and C2 retry/adapter acceptance remain gates. Function-local statement_timeout is not a universal HTTP deadline.

### Approval protection

The definer trigger inspects the actual outer SQL role setting, **not current_user inside the definer** and not JWT user_metadata. Only the existing trusted service role, or a direct postgres maintenance session, may transition approval/type/review identity. Ordinary verified owners may create native pending or external approved, edit allowed content/deadlines/archive state, and retain the same type/status/review metadata. Official creation is reserved for trusted server/maintenance authority. Native→external→native laundering, organizer reassignment and fake ai_feedback review fields are blocked. Restrictive INSERT/UPDATE policies add ownership/state defense in depth without replacing existing SELECT/DELETE policies.

## Legacy official and related workflow review

- **official:** treat an approved, unarchived official event as non-native community participation. Native RPC rejects it. Closed official application dates do not disable HackerMate teammate discovery while the event is still active. No type conversion, seed rewrite or claim of official registration is introduced. NULL/unknown type or NULL/non-approved status fails closed for new participation; the old status-column default backfilled approved in the historical migration, but actual exceptional legacy rows still need classification before release. Do not silently approve them.
- **Partner portals:** existing LegacyPartnerPage track toggles and all private organizer RPCs retain their columns, ACLs and metadata guards. Partner event membership/community behavior uses the same guarded path; no global raw-attendee read reappears. Approved/rejected public projection fallback inconsistencies already present in old read functions remain a documented read-semantics issue, not a reason to accept new registration on rejected events.
- **Rack It Up:** fixed official external URL, guest projection, login/onboarding return path, no automatic community join, explicit profile-listing intent and the About this hackathon heading remain. The exact conversion journey must pass unchanged. No official-site registration/provider action is used.
- **Certificates:** issue-badges/verification and grant_hackathon_winner_badges operate on user_badges/authorized projections, not a new registration writer. Community confirmed does not become a certificate entitlement. Retain admin/organizer proof checks, certificate IDs, public verification privacy and hackathon-name joins.
- **Teams:** confirmed production `hackathon_registrations_team_id_fkey` is ON DELETE CASCADE and is retained. Deleting a team removes its linked registration rows, public discovery/registration-history entries and participation-based access, and frees their confirmed row slots; existing independently stored certificates are not registration rows. No FK change is proposed. SET NULL would preserve rows/capacity but change eligibility and access after dissolution, and would require a separate migration/proposal. Native admission still counts distinct members UNION owner; team links/workspaces remain independently authorized.

## Required application adapter contract (future implementation)

1. Keep the existing bearer-authenticated HTTP endpoint and request `{teamId,reviewedUnknown}`. Within nativeRegistration.ts, call `client.rpc('register_native_hackathon', {p_hackathon_id:eventId,p_team_id:teamId,p_reviewed_unknown:reviewedUnknown})`; validate `{status:'confirmed'|'waitlisted',alreadyRegistered:boolean}` and return it. Never fall back to direct INSERT after contract or add a service-role client. App pre-checks may improve messages but cannot decide admission.
2. Map database authorization failures to controlled authentication/403 messages, known P0001 admission rejections to 409, lock/serialization/deadlock availability errors to retryable 503, and invalid arguments to 400. Log original errors without returning internal SQL details. A retry repeats all fresh checks and is idempotent; no blind server retry beyond the deadline.
3. Shared discovery creation already selects returned status; keep that row authoritative. External confirmation must request the stored `id,status` and base its toast on that status. Remove reliance on client capacity checks; never use stale counts to promise success. Keep metadata merge, duplicate recovery, account-switch checks and native allowCreate=false coverage.
4. Database RPC bypassing HTTP is expected and safe: it applies the full database boundary. This design does not promise that only the HTTP endpoint is callable.

2. Qualify the chosen SQL and adapters locally first; the executable local runner now tests both lock variants and the real matchmaking triggers. Baseline privacy assertions remain. Review the global comparator's expected deadlock as a release failure, not as release qualification.
3. In a separately authorized maintenance release, commit 00-freeze-admission first: table AND column INSERT privileges plus restrictive policy block ordinary old direct writers. 4. Existing-registration reads can still return data. Expansion without the initial freeze is explicitly unsafe and prohibited.
5. Apply contract (02) while still frozen. Verify native direct INSERT denied, community scope/metadata/status rules correct, both RPC entry ACLs correct, all server instances drained/upgraded, and accepted UI behavior for cached clients. Native HTTP payload stays unchanged, but old server builds that raw-INSERT native rows fail closed; never add fallback writes. 6. Only after independent approval of metadata snapshots, PG17.6 qualification, adapters, role negatives, workflow checks, capacity semantics and rollback readiness consider 06-unfreeze. SQL requires writer helpers/NOWAIT and contract markers, rejecting both old comparators; humans must verify full definitions/version convergence and application gates. 7. On failure, roll back an uncommitted DDL transaction. After commit, use 03-rollback-freeze to revoke RPC and direct inserts while preserving records/readers/preferences/cancellation, then fix forward. Rolling the application back to raw-INSERT native code after contract produces safe failures, not restored admission. Never restore the unsafe native policy to regain availability. ## Reference semantics checked

Column and table privileges are distinct; clearing both matters ([PostgreSQL REVOKE](https://www.postgresql.org/docs/current/sql-revoke.html)). Restrictive policies add an AND condition and BEFORE triggers precede WITH CHECK ([PostgreSQL CREATE POLICY](https://www.postgresql.org/docs/15/sql-createpolicy.html)). Event-row locking and transaction snapshots are the database basis for the proposed serialized decision ([PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html)). Function ownership, execution ACLs and hardened search paths need explicit review ([PostgreSQL functions](https://www.postgresql.org/docs/15/sql-createfunction.html), [Supabase functions](https://supabase.com/docs/guides/database/functions)). Supabase's current changelog was checked; its recent timezone advisory reinforces verifying actual server/tzdata versions, without changing the established India-only date contract ([changelog](https://supabase.com/changelog)).
