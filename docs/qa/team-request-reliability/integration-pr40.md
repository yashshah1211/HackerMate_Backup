## Exact future manual QA checklist

Do these only after the founder explicitly authorizes the isolated environment and existing dedicated accounts. Record pass/fail, tested commit, frontend origin and non-secret backend project identifier. Keep credentials, cookies and invite tokens out of screenshots/logs/PRs.

1. **Verify targets before login or mutation.** Inspect the test deployment's build-time `NEXT_PUBLIC_SUPABASE_URL` using an authorized configuration view, then confirm the actual browser Data API/Auth request origin matches that approved project. Check any server-side backend independently. It must differ from production; a Preview domain or staging-like name is insufficient. If configuration, isolation, existing accounts or safe outbound side effects cannot be established, stop and retain BLOCKED. Use only synthetic fixtures in this approved backend, never existing student teams.
2. **Prepare fixtures through existing permissions.** Use separate browser profiles for existing dedicated owner A and applicant B, signing in normally. Owner A creates clearly labeled throwaway teams `QA_PR39_<run>_accept`, `_reject` and `_invite`, with available seats. Track every created fixture. Use `try/finally` cleanup for any automated fixture helper; for manual execution, maintain the same complete cleanup checklist even after a failed case. Do not create accounts or change policies/RPCs.
3. **Explicit request and duplicate protection.** On `/teams/<accept-id>`, B should first see Checking request, then Request to join after verified absence. Mount, refresh and focus must send no request RPC. Activate Request to join once; verify one `request_to_join_team` call with only that team ID and eventual Request sent. A rapid repeated click must not issue another in-flight call. Reload and return from another tab; pending remains accurate. Verify one existing `team_join_request_sent` event only after success, with `{source: "team_detail"}` and no content/identity payload. Check only the synthetic request, using authorized read access, if confirming the stored row.
4. **Real acceptance.** In A's profile, open `/teams/<accept-id>/requests` and accept B through the existing owner UI. Return/focus B's team page, then repeat with browser refresh. Verify Open workspace and membership, no stale Request sent, and `/my-teams` keeps membership separate from pending applications. No new application is sent by refresh. Do not infer acceptance solely from a disappeared pending row.
5. **Separate rejection/deletion.** In B's profile explicitly request `_reject`. In A's profile use the existing request rejection/removal action. Return/focus B, then refresh: Request sent clears, B has no membership or workspace access, and the UI makes no accepted/rejected history claim. Check that no automatic resubmission occurs; a new request requires a new explicit activation.
6. **Logout and account switching, including delayed reads.** Start with B pending on an available fixture. Throttle only its pending-status GET response in DevTools; sign out/switch normally to A while the response is delayed, then release it. B's status must not appear for A. Sign out: public visitor controls only. Sign back as B: fresh scoped status. Repeat A → B → A, navigate to another team, and navigate away/back while a read is delayed. Verify owner/member controls reflect the current account and prior responses cannot restore state. Record no cookies or private response bodies.
7. **Failed reads and explicit recovery.** In B's browser DevTools block only the fixture team's `GET /rest/v1/team_join_requests` status read (match its team and user filters), keeping RPC POSTs untouched. Focus/return or reload. Verify the unknown/error message and Retry status check, no enabled Request to join, no inferred zero/absence and no success analytics. Repeat for the scoped membership GET. Remove the block and activate Retry: only reads occur; verified current pending/membership state returns. Also test a failed refresh after a known pending result and a failed preflight after a previously verified empty result. Do not alter RLS/grants to simulate failure.
8. **Instant invitation, valid and cancelled.** Through an existing owner-authenticated test client on the approved backend, use `supabase.rpc("generate_team_invite_token", {p_team_id: <invite-id>})`; source permissions restrict generation to the owner. Open `/teams/<invite-id>?join=true&token=<URL-encoded-token>` in B's profile. Opening only presents confirmation. Cancel must perform no mutation. Reopen for a fresh confirmation and explicitly confirm: verify `join_team_instantly` receives the exact team ID and token, membership refreshes, stale pending clears and no join-request analytics is emitted. Repeat a stale confirmation after switching accounts: the old confirmation must not join for the new account.
9. **Invalid, absent and genuinely expired tokens.** On a separate available fixture before B becomes a member, use a token with a modified signature to test invalid signature, and `join=true&token=` for the missing-token case. Explicit confirmation must show the server error with no membership, success toast, success analytics or automatic retry. For expiry, use an existing legitimately signed, expired token from the approved QA setup. Editing its expiry invalidates its signature and is **not** an expiry test. The source generator uses a seven-day lifetime; without an existing genuine expired fixture, keep expiry BLOCKED rather than changing clocks, Vault, RPCs, policies or secrets. Confirm pending status still reflects its actual row after failure.
10. **Final checks and cleanup.** Recheck both viewport sizes and keyboard controls with the real shell/fonts; test the normal pending team-invite Accept/Decline path on synthetic fixtures if available. Delete all created throwaway teams/requests/invites/memberships through authorized existing workflows, including leftovers from failed cases; never delete accounts or unrelated rows. Confirm cleanup and re-run read-only status checks. Record each real case as PASS, FAIL or BLOCKED separately.
