## Remaining limitations and delivery record

- STAB-006 is open, and STAB-011 is blocked separately.
- An ambiguous message commit followed by manual retry is an unverified idempotency risk. The frontend in-flight guard is not durable exactly-once delivery; adding a ledger/contract requires separate authorization.
- Per-task serialization orders one mounted client's pending requests while responses remain outstanding; simultaneous clients retain existing database last-writer semantics. A transport failure may settle the client promise before an unknown server outcome. Independent synthetic fault injection allowing that old commit to execute late reproduced the limitation on both baseline and corrected code, not a newly established deployed PostgREST defect. The error path reports uncertainty without success/automatic mutation retry; already queued later intents can still run after that error, and refresh guidance is not an enforced lock. Commit ordering after unknown transport outcomes requires an approved server-side protocol; refresh/reconciliation cannot establish exactly-once semantics. Read-after-write handles acknowledged state, not a global compare-and-swap guarantee.
- Committed membership removal/suspension is enforced at the next READ COMMITTED statement in tested tables. This does not retroactively cancel writes already authorized/in flight before revocation, retract copied/public media or guarantee immediate browser cache erasure.
- Database realtime delete transport/policy behavior and deployed Supabase grants remain production acceptance limits. Table RLS and synthetic callbacks do not establish live subscription revocation.
